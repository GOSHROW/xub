# Native large-integer benchmark prototype

This is experimental measurement code, not the final requested C/ASM product.

## Build and run

```sh
clang -O3 -std=c11 -Wall -Wextra -Werror \
  -I/opt/homebrew/Cellar/openssl@3/3.6.3/include \
  .scratchpad/bench_large.c \
  /opt/homebrew/Cellar/openssl@3/3.6.3/lib/libcrypto.3.dylib \
  -o .scratchpad/large-bench

.scratchpad/large-bench --verify-only

.scratchpad/large-bench --max-bits 4096 --target-ms 5 \
  --output .scratchpad/large-results.csv 2> .scratchpad/large-run.log
```

`--max-bits 16384` additionally measures 16,384-bit inputs; the quadratic
shift-add, bit-prefix, and set-bit candidates are omitted at that size. Native
controls and recursive candidates remain. Each measured output is compared
against `BN_mul` before timing, including the optional larger size.

### Single scalar-leaf tuning variant

The original eight-bit BIGNUM leaf threshold remains the source default and its
original executable/results are preserved. One follow-up variant removes two
levels of BIGNUM API overhead by completing inputs of at most 32 bits in native
scalar registers, still without multiplication instructions:

```sh
clang -O3 -std=c11 -Wall -Wextra -Werror -DSCALAR_LEAF_BITS=32 \
  -I/opt/homebrew/Cellar/openssl@3/3.6.3/include \
  .scratchpad/bench_large.c \
  /opt/homebrew/Cellar/openssl@3/3.6.3/lib/libcrypto.3.dylib \
  -o .scratchpad/large-bench-leaf32

.scratchpad/large-bench-leaf32 --max-bits 16384 --target-ms 5 \
  --output .scratchpad/large-leaf32-results.csv \
  2> .scratchpad/large-leaf32-run.log
```

The scalar square uses the same three-square recursion and 256-entry table.
The scalar direct-product comparator uses set-bit shift-add, choosing the
smaller-magnitude factor to scan; products with both factors at most eight bits
retain the two-lookup midpoint table rule. Results fit `uint64_t` and are copied
into BIGNUM through `BN_set_word`; a static assertion requires a 64-bit
`BN_ULONG`. The square table still occupies 512 bytes. This is one tuning
experiment, not an exhaustive search for optimal thresholds or leaf methods.

The additional scalar validation preserves the random generator state, so the
two leaf configurations receive identical measured input pairs. It checks all
65,536 unsigned 16-bit squares, 10,000 random 32-bit squares and products, and
the maximum 32-bit boundary. All passed, along with the original BIGNUM checks.
Generated ARM64 scalar-square, scalar-product, recursive-square and
direct-Karatsuba bodies contain no multiply instructions or calls to native
multiply/square routines. Runtime metadata prints `scalar_leaf_bits`.

## Comparators

- `copy_control`: input-copy/call/checksum floor; not multiplication.
- `native_mul`: OpenSSL `BN_mul` using the host's native arithmetic.
- `native_equal_aware`: explicitly calls `BN_sqr` for equal-valued inputs.
- `mid_native_square`: the common midpoint routine, with OpenSSL `BN_sqr`.
- `shift_add_short`: direct multiplication scanning the shorter bit length.
- `shift_add_sparse`: direct multiplication scanning the sparser operand;
  counting set bits is included in its measured cost.
- `direct_karatsuba`: software Karatsuba, using the same 256-entry square table
  to implement products of two eight-bit leaves. Highly unequal nodes with an
  eight-bit factor use direct shift-add.
- `recursive_equal_aware`: explicit recursive square for equal inputs,
  otherwise direct software Karatsuba.
- `mid_recursive`: common midpoint with three-square recursion.
- `mid_set_bits`: common midpoint with grouped bitwise rows.
- `mid_prefix`: common midpoint with bit-prefix recurrence.
- `near_native`: smaller operand squared, plus its product with the difference.
- `near_recursive`: recursive square plus direct shift-add with the difference.
  The two near-identity controls are timed only on near/equal workloads.

All software candidates avoid general multiplication in their arithmetic.
The native controls and correctness oracles intentionally use it. The eight-bit
square table is generated by successive odd additions and occupies 512 bytes.

## Measurement procedure

Four default operand widths: 64, 256, 1,024 and 4,096 bits. Eight deterministic
input pairs per width and pattern. Patterns are random balanced, near (positive
gap at most 255), equal, three-set-bit sparse, almost-all-ones dense, one
eight-bit factor, a factor of one, and unequal powers of two. Equal operands are
distinct BIGNUM objects. In the power-of-two workload the larger factor is
2^(n-1), the smaller 2^(n/2); their half-difference contains a run of set bits.

All measured methods are validated and warmed on all eight pairs before timing.
BN_CTX temporary buffers and the output buffer are reused. Calibration doubles
the batch until it lasts at least approximately one millisecond, then scales
repetitions toward five milliseconds per trial. There are five trials, with
algorithm order shuffled each trial. CSV reports median, minimum and maximum
nanoseconds per product. It does not subtract the copy-control floor.

Every product contributes `BN_num_bits(output)` to an observable scalar
checksum. This adds the same scalar overhead to all methods; full results are
validated outside timed regions. There is no per-product decimal conversion or
wide modular checksum. No link-time optimization is used.

## Limits and assembly audit

These are host ARM64 timings, not measurements of a device lacking multiplication
instructions. The custom algorithms use OpenSSL's BIGNUM addition/shift API;
function calls, argument handling and BN_CTX management are included. They are
not hand-optimized limb kernels. The original recursion stops at eight bits;
the single tuning variant moves up-to-32-bit work into scalar leaves. Recursive
overhead can still be substantial. Tables and allocations are
warm. CPU affinity, core selection and frequency are uncontrolled.

BIGNUM has no public set-bit iterator, so the set-bit square scans all n input
positions and performs s row additions. The sparse direct comparator similarly
includes its population scans. These are implementation costs, not mathematical
lower bounds.

The generated ARM64 assembly was inspected. The custom `square_recursive`,
`square_set_bits`, `square_prefix`, `direct_karatsuba`, `shift_add_short`,
`shift_add_sparse`, and `shift_add_selected` arithmetic bodies contain no
MUL-family instructions and no calls to `BN_mul` or `BN_sqr`. Native controls,
oracles, random input generation and clock calculations do contain multiplication.
`near_identity` contains both native and software branches; `near_recursive`
passes the flag selecting the software branch. The linked library's every
internal instruction was not audited; this audit establishes the arithmetic
operations requested by the prototype.

Correctness-only validation passed 65,536 eight-bit leaf products and 433 larger
or boundary operand pairs across all 12 product implementations before timing.
Measured datasets receive additional comparisons against OpenSSL multiplication.
